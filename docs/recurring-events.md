# 繰り返し予定 (#90)

Webの予定フォームで繰り返し条件を設定する。通常フォームから同じダイアログの設定画面へ切り替え、保存しないプレビューで直近3回を確認する。「設定を適用」は入力への反映で、予定の確定は元の画面の「作成／保存」。

## API契約

日時は既存どおりJSTのタイムゾーンなし文字列。終日の終了日は包含日。タイトル・説明・通知件数などの既存制限を維持する。繰り返し予定の事前通知は各単位1〜100（最大100週間）。Discordスケジュールイベントとは併用できず、連携済みの単発は先に解除して保存する。

作成・更新の `recurrence_rule` は以下の構造化条件のみ受け付ける。任意RRULEは受け付けない。

```json
{
  "frequency": "weekly",
  "weekdays": [0, 2],
  "end": { "type": "count", "count": 8 }
}
```

| frequency | 追加項目 |
|---|---|
| `none` | なし。繰り返し解除の明示 |
| `daily` | `end` |
| `weekly` / `biweekly` | `weekdays`: 月曜0〜日曜6、1〜7個、`end` |
| `monthly_date` | `day`: 1〜31、`end` |
| `monthly_weekday` | `nth`: 1〜5、`weekday`: 月曜0〜日曜6、`end` |

`end` は `{"type":"never"}`、`{"type":"until","date":"2026-12-31"}`、`{"type":"count","count":8}` のいずれか。回数は1〜10000で初回を含む開催枠の数。存在しない日付・第5曜日はスキップし、中止しても回数を補わない。初回の開始日は条件に一致する必要があり、不一致は400。

- 更新で条件を省略した場合は維持する。日時移動のみの「この回以降」では、曜日・月の日付も移動量に合わせる。条件を明示した場合は自動補正しない。
- 更新の `scope`、削除クエリの `scope` は `this`（省略時）／`future`。`future` は `expected_series_version` が必須で、不一致は409。最新の一覧を取得して確認し直す。
- レスポンス `recurrence` は単発ならnull。繰り返しは `series_id`、`original_start_at`、`is_exception`、`rule`、`version` を含む。`rule` は入力と同じ構造。
- `POST /events/{guild_id}/recurrence/preview` は `{"start_at":"2026-09-21T19:30:00","recurrence":{...}}` を受け、JST日時の配列（最大3件）を返す。編集権限を検証し、保存と同じ計算を使う。「この回以降」の編集では `event_id` も渡し、回数条件が未変更なら消費済み枠を差し引いてプレビューする。管理画面は `POST /admin/guilds/{guild_id}/events/recurrence/preview`。
- 「この回のみ」で条件を変えることはできない。MCPの既存編集・削除もこの範囲となり、シリーズ操作ツールは追加しない。

## 保存と補充

`event_series` に共通入力JSON・条件JSON・正規化RRULE・JST初回日時・分割終了境界・バージョン・操作者・補充済み期間を保存する。Rust `rrule 0.14` をAPI/Botの `shared/` から使用する。ブラウザのFullCalendarには既存 `events` に実体化した各回を渡す。

`events(series_id, original_start_at)` の一意制約で重複を防ぐ。`event_series_exceptions` は元の開始日時と個別変更済みIDを保持し、IDがnullなら中止。変更／例外記録は同じトランザクション。シリーズ行をロックして補充し、例外を上書きしない。全削除もシリーズ→予定の順にロックし、ルールを削除する。

初回は先の予定でも必ず保存する。通常は現在から730日先まで補充し、Botの通知判定前に日単位で不足を補う。認可後の一覧取得でも要求期間に重なる回を生成する（期間より前から続く複数日予定を含む）。展開には件数・反復上限を設け、上限・計算失敗を空一覧にしない。

「この回以降」は移動後の日時でなく元の開催枠で旧シリーズを閉じ、新シリーズへ分割する。過去は変更しない。変更しなかった回数条件は消費済み枠を引く。新旧は元のJST開催日で対応付け、対応する回のID・個別変更・中止を維持する。対応しない個別変更済みの回や添付のある回は単発として残す。移動先が中止済み枠と衝突する変更は400となり、全体をロールバックする。

添付・共有リンクは各回のIDに属する。新規作成時の添付は初回だけ。複製は選んだ回を単発として作成する。「この回以降の削除」は個別変更済みの回とその添付も削除する。

## 通知・外部連携

- 自動生成ではWebhookを発行しない。利用者のシリーズ操作は対象回の1件を通知し、`change_scope` と `recurrence` を追加する。
- Bot／Pushは既存の各回ID・発火時刻の重複抑止を使う。同じ発火時刻の複数設定は1件。Discord通知の再起動時の再送可能性は従来どおり。
- iCalは安定した各回IDのUIDを持つVEVENTのみ。RRULEを重ねて出力しない。繰り返しは過去366日〜未来730日、単発の既存範囲（過去365日以降、未来制限なし）は維持する。
- Botの期間指定なし一覧も繰り返しは過去366日〜未来730日に制限し、画面に範囲を表示する。

## 移行と戻し方

新規マイグレーション `20260921000000_create_event_series.sql` と `20260921000001_mark_generated_occurrences.sql` をAPI起動時に適用する。既存予定は2つの追加列がnullの単発となり、日時・ID・添付を変更しない。APIとBotを同じ版に揃える。

戻す前にAPI／Botを停止し、DBのバックアップを取る。`api/rollback/20260921000001_revert_generated_occurrences.sql`、`api/rollback/20260921000000_revert_event_series.sql` の順に実行するとルール・例外を退避した上で追加列とテーブルを除去する。生成済みの各回と添付・共有リンクは単発として残り、未生成の将来分は補充されなくなる。適用記録とイメージの戻し方は [運用手順](operations.md#マイグレーションが入った版から戻す) に従う。退避テーブルの名前が既にある場合は上書きせず停止するので、先に退避先を確認する。

作成数の日別・月別推移は補充した回を除外する（`generated_from_series`）。単発への切り離しでもこの印は保持する。現在の総予定数・通知設定の内訳は各回を数える。有限ルールは最後の開催枠より後の境界を `end_before` に保存し、長時間・終日予定の重なりを含めたSQL条件で終了済みシリーズを除外する。
